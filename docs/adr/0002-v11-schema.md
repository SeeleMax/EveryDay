## 1. 背景与问题

交接文档 P1 的第一条任务是：

> 实现本文档**附录**的全部 Schema 变更

但实际收到的文档里，**附录只有「参考资料」清单，没有 Schema 正文**；
同时被引用的「技术文档」章节（需求 1~10）也不存在。
另一处相关表述是「数据库 Schema 需要变更时必须暂停并提问」（§7.1）。

因此 P1 面临一个选择：

1. 停下来等信息 → 阻塞整个 v1.1
2. 按 P2~P5 的需求描述反推设计，明确标注为「待确认」，继续推进

**决定：选 2。** 理由：需求描述虽然零散，但对数据的要求足够明确
（优先级、标签、子任务、依赖、历史统计、回收站、番茄钟、屏幕时间）；
反推设计可以在不阻塞的前提下把结构定下来，确认后再调整也只是增量迁移。

## 2. 决定：v1.1 的表结构

### 2.1 `task_item` 扩展三个字段

| 字段 | 类型 | 默认 | 用途 | 需求来源 |
|---|---|---|---|---|
| `priority` | INTEGER | 2 | 优先级，0=紧急 1=高 2=普通 3=低 | P2「列表按优先级排序」 |
| `parent_task_id` | INTEGER NULL | NULL | 子任务指向父任务 | P2「子任务可折叠」 |
| `deleted_at` | TEXT NULL | NULL | 软删除时间戳（回收站） | P4「软删除 + 当天回收站」 |

**优先级数值越小越优先**，这样 `ORDER BY priority` 天然就是「重要的在前」，
列表排序不必再倒序处理。

### 2.2 新增六张表

| 表 | 用途 | 需求来源 |
|---|---|---|
| `task_tag` | 任务的多个标签 | P2「标签 chip 展示」 |
| `task_dependency` | 前置依赖的边（有向图） | P2「依赖 + 循环依赖检测」 |
| `task_history` | 任务事件的流水 | P4「完成率热力图、连续打卡」 |
| `focus_record` | 每段专注的起止与时长 | P3 番茄钟 / P4 专注时长 |
| `screen_time_record` | 按「日期+应用」聚合的秒数 | P5「屏幕时间采样、会话合并」 |
| `reminder_log` | 每个任务每天的提醒与推迟状态 | P3「通知 + 稍后提醒」 |

## 3. 关键设计取舍

### 3.1 `parent_task_id` 不加外键

SQLite 的 `ALTER TABLE ADD COLUMN` 只在默认值为 NULL 时允许带 `REFERENCES`，
而且给已有表补外键需要**整表重建**（建新表 → 拷数据 → 删旧表 → 改名），
在迁移里做这件事的收益（防止父子指向不存在的 id）低于风险
（重建期间中断会让任务表处于半成品状态）。

v1.1 的删除是**软删除**，父任务不会真的消失，因此不会产生孤儿。
层级完整性由 P2 的服务层负责校验。

### 3.2 `task_history` 不加外键

任务被彻底清理（`purge_deleted`）后，历史必须留存——否则「完成率热力图」
会随着删除任务而缩水，统计就失真了。所以这张表只记 `task_id` 数字，
不建立引用关系。

### 3.3 `focus_record` 用 `ON DELETE SET NULL`

与历史不同，专注记录**关联**任务但不**属于**任务：任务被删掉后，
「我今天专注了 90 分钟」这个事实仍然成立，所以把 `task_id` 置空即可。

### 3.4 `screen_time_record` 存聚合值而不是采样点

P5 要求 2 秒采样一次，一天 12 小时就是 21600 个样本。
按样本存表会在几个月内把库撑到几十万行，而统计面板只需要「某天某应用用了多久」。
因此服务层做会话合并后 **UPSERT 累加**，表的行数量级是「天数 × 应用数」。

### 3.5 番茄钟设置、通知开关等放进 `app_settings` 键值表

`app_settings` 是键值表，新增配置项**不需要迁移**——
这是 v1.0 选择键值存储的直接收益。v1.1 新增的键：
`pomodoro_minutes`、`pomodoro_break_minutes`、`notifications_enabled`、
`screen_time_enabled`、`screen_time_idle_minutes` 等。

### 3.6 迁移幂等性的实现方式

SQLite 没有 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`。
原来的执行器用 `executescript` 一把梭，只要有一条重复就会中断，
剩下的语句全部丢失，迁移文件谈不上幂等（而 D03 明确要求幂等）。

改法：在执行器里**按语句切分执行**（用 `sqlite3.complete_statement`，
字符串字面量里的分号不会被误切），并把「该对象已存在」类错误
（`duplicate column name` / `already exists`）视为已生效、跳过继续。
DDL 与账本写入放在同一个事务里，要么都成，要么都不成。

## 4. 被否决的方案

| 方案 | 否决原因 |
|---|---|
| 新建 `task_v11` 表并迁数据 | 所有查询与仓储都要改，收益仅是规避 `ALTER TABLE` 的限制；而幂等问题已经在执行器层面解决了 |
| 标签存成逗号分隔字符串 | 无法建索引，「按标签筛选」只能全表扫；`task_tag` 连表可以直接走索引 |
| 子任务用独立表 `subtask` | 子任务与普通任务字段完全一致，独立表会导致查询、排序、统计都要写两套 |
| 回收站用 `deleted_task` 独立表 | 恢复时要跨表搬回并重建行号；软删除只是加一个时间戳，恢复就是置空 |
| 屏幕时间按原始样本存 | 见 3.4，行数膨胀两个数量级 |

---

## 5. 影响

* 迁移 `002` 之后，`task_item` 的每一行都会带上三个新字段（旧行取默认值）。
* `TaskRepository.list_all()` 默认**排除**软删除的任务；
  需要回收站内容时显式传 `include_deleted=True` 或调用 `list_deleted()`。
* 六个新仓储在 `everyday/db/repositories.py`，与既有仓储同一风格。
* 旧版本（v1.0.0）的可执行程序无法读取带 `002` 的数据库——
  `schema_migrations` 里多了一条它不认识的记录，但**读取不会失败**，
  因为新列都有默认值且旧代码不查询新表。降级是安全的。
